# 공개 배포 저장소 사용 안내

2026-11-05 결정. 미니 시리즈의 공개 다운로드 및 자동 업데이트 배포처는 [Esper80/mini-app-releases](https://github.com/Esper80/mini-app-releases) 하나를 공통으로 사용한다.

## 적용 범위와 현재 상태

- 각 앱의 본체 소스와 개발·검증은 기존 비공개 저장소에서 관리한다.
- 공개 저장소에는 공개 배포가 승인된 실행파일, 필수 고지·배포 자료, 사용 안내 및 업데이트 메타데이터만 둔다. 앱 본체 소스, 개인 설정, 로그, 계정 정보와 토큰을 복사하지 않는다.
- EXE는 Git 커밋이나 README 첨부 대신 이 저장소의 **GitHub Releases 자산**으로 배포한다.
- 이 문서는 운영 방법과 전환 방향을 기록한 것이다. 자동 업데이트 구현·고정 파일명 전환·기존 CI 변경·실제 릴리스 게시가 완료되었다는 뜻이 아니다.
- 기존 비공개 릴리스와 과거 검증 기록은 보존한다. 문서화만을 이유로 과거 파일·태그를 이동하거나 일괄 개명하지 않는다.

## 앱 식별과 실행파일 이름

| 앱 ID | 제품 | 전환 목표 EXE 이름 |
| --- | --- | --- |
| mini-audio | Mini Audio | MiniAudio.exe |
| mini-resource-monitor | Mini Monitor | MiniMonitor.exe |
| mini-capture | Mini Capture | MiniCapture.exe |
| mini-mp3-maker | Mini MP3 Maker | MiniMP3Maker.exe |
| mini-tv-link | MiniTV Link PC 프로그램 | MiniTVLink.exe |

고정 이름은 앞으로의 전환 목표다. 실제 패키징·검사·문서를 함께 수정하고 검증한 버전부터 적용한다. TV Link의 이름은 이미 고정형이다. 현재 사용자에게 안내할 파일 이름은 실제 게시된 자산과 대조한다.

버전은 EXE 내부의 FileVersion/ProductVersion, 앱 정보, 릴리스 기록 및 업데이트 목록에서 관리한다. 앱별 버전 형식은 유지하며 Capture는 표시 버전 major.minor와 내부 Cargo major.minor.0을 구분한다.

## 공동 저장소에서 릴리스를 구분하는 방법

하나의 앱 버전당 하나의 릴리스를 만드는 운영안을 사용한다. 앱별로 버전이 독립적이므로 공개 배포 태그에는 앱 ID를 포함한다. 예: `mini-audio/v1.0.11`, `mini-capture/v1.2`. 예시 번호는 실제 배포 또는 최신 버전 선언이 아니다.

공개 저장소 태그는 이 저장소의 배포 기록 커밋을 가리킨다. 비공개 저장소의 빌드 소스 태그와 같은 커밋이라는 뜻이 아니다. 비공개 검증 기록에서 소스 커밋 → 빌드 후보 → 파일 해시 → 공개 릴리스/자산의 대응을 남긴다. 소스 태그·공개 태그를 혼동하거나 비공개 커밋을 이 저장소에 가져오지 않는다.

저장소 전체의 `releases/latest`는 앱별 최신 버전을 구분하지 못한다. 앱은 이 값을 자기 앱의 최신 버전으로 사용하지 않는다.

## 앱별 업데이트 목록

공통으로 읽을 안정 채널 목록은 `updates/stable.json`을 제안 경로로 예약한다. **아직 작동하는 목록을 게시한 것이 아니며**, 최초 구현 때 다음 항목과 스키마 버전·서명 방식·실제 URL을 확정하고 각 앱 문서를 맞춘다. 이 문서에 적힌 경로를 이미 존재하는 파일로 간주하지 않는다.

앱별 항목에는 최소한 앱 ID, 내부 버전, 채널, Windows 아키텍처, 공개 릴리스 태그/ID, EXE 자산 이름/ID와 특정 릴리스 다운로드 URL, 바이트 크기, SHA-256 및 검증용 서명 정보를 연결한다. 한 앱의 목록을 갱신할 때 다른 앱 항목을 보존한다. 예시·미검증 버전·초안 링크는 활성 목록에 넣지 않는다.

클라이언트 흐름:

1. 목록에서 자신의 앱 ID·채널·아키텍처만 선택한다.
2. 현재 EXE 내부 버전과 숫자 단위로 비교한다. 같은 버전·구버전·사전 출시 버전은 기본 자동 설치 대상에서 제외한다.
3. 조회 시 확인한 **특정 릴리스의 EXE**를 내려받고 크기·해시·서명을 검증한다. 다운로드 때 다시 움직이는 latest 주소를 사용해 다른 버전 파일과 섞지 않는다.
4. 사용자가 정한 자동 설치 옵션과 앱별 작업 제한을 확인한다.
5. 정상 종료 후 보조 프로세스가 같은 실행 경로의 EXE를 교체하고 재실행한다. 설정·인증·사용자가 저장한 파일은 보존한다.

개발자 토큰을 앱에 내장하지 않는다. 공개 다운로드는 익명 접근을 기준으로 검사한다. 해시는 파일 손상 검출에 사용하며, 게시자 진위를 위한 서명 정책도 최초 자동 설치 구현에서 확정한다. 인증 실패·오프라인·403/429·검증 실패를 최신 버전으로 표시하지 않는다.

## 실제 게시 순서

이 절차는 이후 승인된 릴리스 작업에 적용한다. 문서를 저장하는 작업은 바이너리 게시나 자동 업데이트 활성화 승인으로 확대하지 않는다.

1. 대상 앱·버전·소스 커밋·공개할 파일 범위와 해당 작업의 게시 승인을 확인한다.
2. 비공개 소스 저장소의 기존 빌드·검사·고지 절차를 수행한다. 관련 앱의 필수 자료와 실행파일만 별도 배포 폴더에 모은다.
3. 파일 이름, 내부 버전, OS/아키텍처, 바이트 크기와 SHA-256을 기록한다. 검증한 후보를 게시 직전에 임의로 다시 빌드하지 않는다.
4. **Esper80/mini-app-releases**의 Releases에서 앱 ID가 포함된 새 태그와 제목으로 **초안**을 만든다. Tag 대상은 이 공개 저장소의 배포 기록 커밋이다.
5. 초안에 승인된 EXE와 앱별 필수 고지·소스/교체 자료를 올린다. 제목·설명에 앱 이름·내부 버전·지원 환경·변경 사항·필요한 사용 안내를 기재한다.
6. 초안 자산을 재다운로드해 검증 후보와 크기·해시를 비교한다. 태그/제목/내부 버전/목록에 들어갈 버전이 대응하는지 확인한다.
7. 릴리스를 정식 게시하고 익명으로 해당 자산의 실제 다운로드가 가능한지 확인한다.
8. 확인이 끝난 **그 앱의** 안정 채널 목록 항목만 갱신한다. 목록 갱신은 사용자에게 자동 설치 후보를 노출하는 활성화 단계이므로 EXE 게시·검증보다 앞서 하지 않는다.
9. 공개 README의 앱별 안내와 비공개 저장소의 배포 기록을 갱신하고, 게시된 릴리스·목록·다운로드의 일치를 재확인한다.

릴리스 게시와 목록 갱신은 서로 다른 저장 작업이다. 중간에 실패하면 미검증 항목으로 목록을 바꾸지 않는다. 앱은 목록에서 지정된 자산이 없거나 검증에 실패하면 기존 버전을 유지해야 한다.

## 앱별 기존 배포 제약

- **Capture:** 릴리스에 직접 올리는 자산은 EXE 하나라는 기존 계약을 유지한다. 공통 업데이트 목록은 저장소 문서/메타데이터 경로로 분리하고 Capture 릴리스에 별도 updater·ZIP·체크섬 파일을 임의로 추가하지 않는다.
- **Audio:** 기존 구성요소 고지와 라이브러리 교체 자료 배포 요구를 보존한다. 본체 소스 공개로 대체하지 않는다.
- **MP3 Maker:** 기존 내장 의존성의 고정 버전·해시 검증과 필요한 구성요소 소스·빌드 자료 제공을 보존한다. 개발용 미디어·캐시는 게시하지 않는다.
- **TV Link:** PC EXE 업데이트와 기기 펌웨어 배포는 별개다. PC 목록에서 .bin을 선택하거나 PC 업데이트를 이유로 기기를 자동 플래시하지 않는다. 기기 펌웨어는 따로 검증·승인한 범위에서만 게시한다.
- **Monitor:** Windows 자동 실행·바로가기의 실행 경로와 설정 저장을 보존한다.

각 앱의 상세 작업 제한과 검증 요구는 해당 비공개 저장소의 `docs/AUTO_UPDATE.md` 및 기존 개발 문서를 따른다.

## 실패·취소·회수와 복구

- 초안/검증 실패 자산은 안정 목록에 올리지 않는다. 자동 재시도는 제한하고 이미 게시된 동일 버전의 EXE를 다른 바이트로 덮어쓰지 않는다.
- 문제가 있는 업데이트는 우선 해당 앱 항목을 설치 후보에서 제외하거나 직전 검증 항목으로 되돌려 추가 배포를 막는다. 다른 앱 항목은 유지한다.
- 목록을 되돌려도 이미 설치된 앱이 자동으로 다운그레이드되지는 않는다. 수동 복구 안내 또는 새 수정 버전을 준비한다.
- 교체 실패는 로컬 백업으로 복구하고, 새 앱의 정상 시작이 확인된 뒤 백업을 정리하도록 구현한다.
- 최초 전환에서는 기존 버전 포함 파일명을 가리키는 바로가기/자동 실행 등록을 확인한다. 구버전에 updater가 없다면 최초 지원 버전은 한 번 수동으로 받아야 한다.
- 배포 파일이 모두 공개된다는 점을 전제로 공개 범위를 확인한다. 기존 소스 저장소의 공개 설정은 바꾸지 않는다.
